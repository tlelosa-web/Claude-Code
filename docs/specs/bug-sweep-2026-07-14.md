# Spec: Bug Sweep — 5 correctness fixes found during general audit

**Status:** Confirmed — Tebello approved all 5, proceed to build (2026-07-14).
**Origin:** Tebello asked "check for other bugs" after the All/Closed toggle fix (Batch 21).
Found via a `reviewer` agent broad sweep, each finding independently re-verified by reading
the live code before this spec was written.

## Fix 1 — Re-upload PDF crashes (BLOCKER)
`routes/sales_orders.py` `reupload_order()`, the POST branch that renders the parsed-review
page (~line 680): `render_template('sales_orders/upload.html', parsed=parsed,
existing_so=so, json_parsed=..., reupload_mode=True)` omits `payment_status_options`, which
the shared template (`templates/sales_orders/upload.html:79`,
`{% for option in payment_status_options %}`) iterates unconditionally once `parsed` is
truthy. Iterating Jinja's default `Undefined` raises `UndefinedError` → 500. The sibling
`upload_order()` route already passes `payment_status_options=PAYMENT_STATUS_OPTIONS`
(already imported in this file from `models`) on both its branches — `reupload_order()` was
never updated to match.

**Fix:** add `payment_status_options=PAYMENT_STATUS_OPTIONS` to the `render_template` call in
the POST branch of `reupload_order()` (~line 680-684). The GET branch (~line 691) doesn't need
it — `parsed` is absent there so the `{% if parsed %}` block (and the loop inside it) never
renders.

**Test:** POST a valid PDF to `/sales-orders/<id>/reupload` for an existing SO, assert 200 (not
500) and that the payment status `<select>` renders with options.

## Fix 2 — `create_from_shortfall` disagrees with the Stock Report it's launched from
`routes/purchase_orders.py` `create_from_shortfall()` (~line 293-297) filters
`Item.qty_on_hand <= Item.reorder_point` (raw on-hand). The Stock Report's "below reorder"
flag (`routes/reports.py:56`) and the Dashboard reorder stat card both use demand-netted
`available_qty = qty_on_hand + qty_on_order - qty_committed`. Since the button lives on the
Stock Report page, a user can see an item NOT flagged (available_qty above reorder point
because stock is already on order) yet have it added to the new PO anyway — or see an item
flagged as short and have it silently skipped because raw on-hand alone isn't below the
reorder point.

**Fix:** reuse `services/demand.py`'s `get_qty_on_order_bulk()` / `get_qty_committed_bulk()`
in `create_from_shortfall()`, compute `available_qty` the same way `reports.py:55` does, and
filter/select on `available_qty <= reorder_point` instead of raw `qty_on_hand`. No new
tuples/logic — copy the exact netting expression already used in `reports.py`.

**Test:** item with `qty_on_hand` below reorder_point but `qty_on_order` covering the gap →
NOT included in the generated PO. Item with `qty_on_hand` above reorder_point but heavy
`qty_committed` pushing `available_qty` below it → IS included.

## Fix 3 — `confirm_pick` missing the `Cancelled` guard `mark_complete` has
`routes/works_orders.py` `confirm_pick()` (~line 157-159) only checks
`if wo.status == 'Complete'`. Its sibling `mark_complete()` (~line 46-52) checks both
`'Complete'` and `'Cancelled'`. Not reachable via the current UI (the button only renders for
Open/In Progress on the detail page), but a direct POST to a cancelled STOCK-type WO would
issue stock and silently un-cancel it.

**Fix:** add the same guard block confirm_pick is missing:
```python
if wo.status == 'Cancelled':
    flash(f"Picking List {wo.wo_number} is cancelled and cannot be picked.", "error")
    return redirect(url_for('works_orders.view_order', order_id=order_id))
```

**Test:** POST to `/works-orders/<id>/confirm-pick` on a Cancelled STOCK-type WO → flash error,
no stock issued, status unchanged.

## Fix 4 — Unguarded `None` arithmetic/formatting on stock value and cost fields
Two separate call sites, same root cause (`Item.qty_on_hand`/`avg_cost`/`last_cost`/
`excl_price`/`incl_price` are nullable per `models.py`, and Batch 19 removed the CSV-import
path that used to backfill `qty_on_hand` on every existing row, so a legacy NULL can persist
indefinitely):

- `routes/reports.py:61` (`stock_data`) and `:110` (`stock_export_csv`):
  `stock_value = item.qty_on_hand * item.avg_cost` — no guard, despite `available_qty` one
  line above already being guarded (`(item.qty_on_hand or 0.0)`, `reports.py:55`). Fix:
  `stock_value = (item.qty_on_hand or 0.0) * (item.avg_cost or 0.0)` at both sites.
- `routes/items.py:21-24` (`catalogue()` AJAX JSON): `f"R {item.last_cost:,.2f}"` etc. for
  `last_cost`/`avg_cost`/`excl_price`/`incl_price` — crashes on `None`. Fix: default each to
  `0` before formatting, e.g. `f"R {item.last_cost or 0:,.2f}"`.

**Test:** an `Item` row with `avg_cost=None` (or `qty_on_hand=None`) → `/reports/stock/data`,
`/reports/stock/export-csv`, and `/items` (AJAX) all return 200, not 500.

## Fix 5 — `qty_required` arithmetic unguarded (latent, low severity)
`BOMLine.qty_required` is nullable with no default. `services/doc_generator.py` (~line 48, 76)
and `routes/works_orders.py` (`mark_complete` ~line 61, `confirm_pick` ~line 163) all do
`bom_line.qty_required - bom_line.qty_issued` / `line.qty_required - available_qty` with no
guard. No current creation path leaves it NULL, so this is defensive hardening, not a live
bug — apply `(bom_line.qty_required or 0.0)` consistent with the guarding already present
elsewhere in the same functions.

**Test:** optional — only add if it doesn't require awkward fixture machinery to force a NULL
`qty_required` through the ORM; a code-level guard without a dedicated test is acceptable here
per the "latent, no live path" framing in this spec.
